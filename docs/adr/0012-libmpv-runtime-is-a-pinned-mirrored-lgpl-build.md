# 12. The in-process libmpv runtime is a pinned, mirrored LGPL build

Date: 2026-11-04

Status: draft — accepted when [#57](https://github.com/shidot3m/aniplayer/issues/57) lands the runtime in the archive and cuts the subprocess path.

Supersedes the playback-runtime reason of [ADR 0010](0010-mpv-subprocess-as-the-only-playback-backend.md): that ADR rejected in-process FFI because "the pinned official build carries no `libmpv-2.dll`". The reason is confirmed and is no longer an obstacle — a build that does carry it is chosen here. Part of the [#53](https://github.com/shidot3m/aniplayer/issues/53) epic.

## Context

ADR 0010's rejection was about the _official_ release, and the official release still says it. Measured for this ticket: `mpv-v0.41.0-x86_64-w64-mingw32.zip` (SHA-256 `a49811c0…`, the archive `scripts/get_mpv.py` already pins) holds one inner build archive of 27 entries — `mpv.exe`, `mpv.com`, two registration scripts and 23 DLLs (`avcodec-62.dll` … `zlib1.dll`) — and no `libmpv-2.dll`; the listing is in [`docs/evidence/54/probe.txt`](../evidence/54/probe.txt). So the source is chosen anew, not resurrected.

The predecessor's CI took the DLL from `shinchiro/mpv-winbuild-cmake`. Checked rather than remembered: that repository is **not** archived and still publishes (`20261103`, mpv `v0.41.0-1421-ga687796d9`), but it publishes no digests, states no license, and keeps only ~30 releases (the oldest surviving one is from 2026-09-23). `zhongfly/mpv-winbuild` is an active MIT-licensed fork of the same toolchain that checks mpv hourly, releases on every relevant commit (two on 2026-11-03 alone), names each tag `<date>-<mpv-sha>`, and publishes a `sha256.txt` inside every release — while documenting the same limit: builds are retained for the last 30 days.

mpv's own CI does build libmpv for Windows (the `win64` job uploads a `libmpv-<ver>-<run-id>-…-gpl` and a `-lgpl` artifact), but workflow artifacts expire and need authentication to download, so they give no fixed URL. MSYS2 ships `libmpv` as a pacman package whose fetch is a dependency graph, not one digest-pinned artifact. Building it ourselves in this repo's CI is durable and remains the escape hatch, at the cost of owning a MinGW/clang toolchain build.

## Decision

- **Artifact**: `mpv-dev-lgpl-x86_64-20261103-git-46787be250.7z` from `zhongfly/mpv-winbuild` release `2026-11-03-46787be250` — mpv `46787be2502556586b6a5fea9ebd595f5cd9b713` (`mpv v0.41.0-1434-g46787be25`), FFmpeg `N-128356-gb8f159858`, clang, x86_64. The upstream archive's SHA-256 is `ce2563d352aac81c2e6e9b2b63e846ec847f4bdabdec74fb14c5b29049c161d7`, taken from that release's own `sha256.txt`.
- **LGPL flavor, chosen deliberately.** The build applies `compile-lgpl-libmpv.patch`: mpv is configured `-Dgpl=false` and FFmpeg loses `--enable-gpl` plus the GPL-only packages (x264, x265, avisynth, libdvdnav, libdvdread, libzvbi …). mpv's own `Copyright` file states that a build without GPL-only files is distributed under LGPL v2.1 or later, which is the arrangement a distributed app can actually satisfy — the library stays a replaceable file, and the app is not forced into a copyleft license it has not chosen. The codec set the catalog needs survives: HEVC Main 10, AV1 (dav1d), VP9 (libvpx), Opus, AAC all decode through FFmpeg's own LGPL decoders, and the gate below proves the case that used to decide the whole design.
- **Mirror, because retention is the real constraint.** The bytes are repacked unchanged into `libmpv-2-20261103-git-46787be250-lgpl.zip` (SHA-256 `c53d9c77c026740c14e479dbdbb1941d76585b2219ced79ca4c92cf65f33da15`) and published under the release tag `libmpv-20261103-git-46787be250-lgpl` of this repository — a tag nothing prunes, unlike the upstream's thirty-day window. `scripts/get_libmpv.py` fetches that asset by its fixed URL, through `gh` because the repository is private, and pins both the archive digest and the digest of `libmpv-2.dll` itself (`63afb25809223c2893bdbcdbc7aa744cf32739cba403dcf0c8ca38a2858589e8`). A pin that a third party can expire is not a pin.
- **What the artifact carries.** `libmpv-2.dll` is self-contained: FFmpeg and every other dependency are linked statically, so no `av*`/`lib*` DLL belongs beside it — `objdump -p` over the pinned DLL lists 47 imports and the only non-Microsoft one is `vulkan-1.dll`, which the portable archive already ships next to `mpv.exe` and which this machine's `System32` provides ([`docs/evidence/54/probe.txt`](../evidence/54/probe.txt)). The mirror zip also carries `NOTICE.md`, `LICENSE.libmpv` (LGPL 2.1) and `LICENSE.ffmpeg` (LGPL 3) so the runtime travels with its terms, plus the upstream `include/mpv/*.h` headers, which are the contract #56 binds against: `scripts/get_libmpv.py` unpacks all of it into `.cache/libmpv-<pin>/` and stages only the four runtime files into the build directory.
- **Sonames are one major ahead, and that is fine.** Today's bundled runtime exposes `avcodec-62`, `avformat-62`, `avutil-60`, `swresample-6`, `swscale-9`; the pinned build's static FFmpeg is master (`Lavc63`/`Lavf63` in the binary, `ffmpeg-version = N-128356`). The two never meet in one process: the DLL is loaded in-process, `mpv.exe` runs as a child with its own set, and #57 retires the `av*-62` group together with the subprocess path.
- **Client API is pinned and proven.** `MPV_CLIENT_API_VERSION` in the shipped header is `MPV_MAKE_VERSION(2, 6)`, and `mpv_client_api_version()` answers `0x00020006` from the DLL. All 21 symbols the in-process backend needs resolve from it — the list `docs/evidence/54/gate_libmpv.py` checks: `mpv_client_api_version`, `mpv_create`, `mpv_create_client`, `mpv_initialize`, `mpv_terminate_destroy`, `mpv_set_option_string`, `mpv_set_property_string`, `mpv_get_property_string`, `mpv_free`, `mpv_command`, `mpv_command_string`, `mpv_command_async`, `mpv_observe_property`, `mpv_wait_event`, `mpv_request_event`, `mpv_request_log_messages`, `mpv_get_property`, `mpv_set_property`, `mpv_wakeup`, `mpv_error_string`, `mpv_hook_add`.
- **The HEVC gate passes on this machine.** `src-tauri/tests/fixtures/hevc_aac.mkv` is HEVC Main 10 `yuv420p10le` and this box has no HEVC decoder installed (`Get-AppxPackage *hevc*` counts zero packages, measured in `probe.txt`). Loaded through `libmpv-2.dll` with `wid` set to a window this process owns, `vo=gpu-next`, `hwdec=auto-safe`: `VO: [gpu-next] 128x96 yuv420p10`, `video-codec = H.265 / HEVC (High Efficiency Video Coding)`, `video-out-params/pixelformat = yuv420p10`, `hwdec-current = no` (the bundled decoder did the work), `time-pos = 4.016845` of `duration = 4.023000` with `eof-reached = yes`, and a screen capture of the host window holds the decoded picture. Evidence, including the harness that produced it: `docs/evidence/54/`. The same run passes for the GPL flavor and for the shinchiro build, so the choice between them is a licensing choice, not a capability one.

## Considered options

- **Official mpv release** — impossible: no `libmpv-2.dll` (measured above).
- **`shinchiro/mpv-winbuild-cmake`** — rejected: live but unlicensed, publishes no digests, and keeps the same ~30-release window; zhongfly builds the same toolchain more often and publishes digests.
- **GPL flavor** — rejected on licensing grounds only: identical gate result, larger obligations (copyleft over the whole combined work) for codecs this app does not need.
- **mpv CI artifacts / MSYS2 packages** — rejected: expiring artifacts behind authentication, and a package manager's dependency graph, neither expressible as one fixed URL plus one digest.
- **Self-built in this repo's CI** — held as the fallback if the mirror ever has to move: durable and fully ours, but it puts a Windows cross-toolchain build under our maintenance.

## Consequences

- Moving the pin is a code change: the version string and both digests live in `scripts/get_libmpv.py`, and the gate above is the check a bump has to pass again. #57 automates re-uploading the mirror asset.
- `libmpv-2.dll` is 101.8 MB unpacked against the ~70 MB `mpv/` folder of today, so the portable archive grows; the subprocess runtime leaves with it in the same pass (#57).
- The app's own license has to be written down before the archive is distributed: an MIT-style permissive license is compatible with shipping an LGPL library beside it, and the repo currently carries no license file at all. The notices the archive must keep are listed in the artifact's `NOTICE.md`.
- A decoder fault now lands inside the app process instead of killing only the player window; containing that is #56's problem, not this decision's.
