# 17. No subtitle control: the catalog delivers no text track to show

Date: 2026-11-05

Status: accepted ([#64](https://github.com/shidot3m/aniplayer/issues/64)); resolves the subtitle line [ADR 0014](0014-webview-is-the-only-playback-backend.md) left open

## Context

mpv picked an embedded text track on its own: `--slang=en,ru` ordered the preferred languages, and the player needed no control for it ([ADR 0010](0010-mpv-subprocess-as-the-only-playback-backend.md)). The webview stack that replaced it can show timed text too — hls.js parses WebVTT renditions and CEA-608 carried inside the video stream, and both land as `TextTrack`s on the media element — but nothing in the player reads them ([ADR 0014](0014-webview-is-the-only-playback-backend.md)). `PlayerVideoViewport` therefore renders a `<video>` with no caption track, and the two caption lints were suppressed in the source to keep CI green.

Whether that is a lost feature or an unusable capability is a measurement question, not a taste question, and [docs/evidence/64](../evidence/64/README.md) answers it on the live CDN (2026-11-05: one sample of 25 Releases spread across the id range the catalog occupies, walked by both probes — `catalog_probe.py` reads the playlists it names, `cea608_probe.py` reads the segments inside them):

- **Playlists**: every one of the delivered HLS playlists is a Media Playlist — no `#EXT-X-STREAM-INF` in any of them. The complete tag set the catalog uses is `EXTM3U`, `EXT-X-VERSION`, `EXT-X-TARGETDURATION`, `EXT-X-MEDIA-SEQUENCE`, `EXT-X-PLAYLIST-TYPE`, `EXT-X-INDEPENDENT-SEGMENTS`, `EXT-X-ENDLIST` and `EXTINF`. The tag that would announce a rendition, `#EXT-X-MEDIA:`, appears nowhere — `EXT-X-MEDIA-SEQUENCE`, which shares its prefix and appears in every playlist, is a different tag and says nothing about text — and no playlist names a `.vtt` or `.srt` resource. RFC 8216 §4.3.4 puts `#EXT-X-MEDIA` among the Master Playlist tags and states that Master Playlist tags MUST NOT appear in a Media Playlist — so a segmented subtitle rendition has no place in which the CDN could announce it to a player that is handed a tier's Media Playlist directly, which is exactly what the AniLibria API hands out.
- **Segments**: the PMT of every scanned segment declares two elementary streams — H.264 (`stream_type 0x1b`) and AAC (`0x0f`) — with no descriptor and no third stream: neither the ATSC A/52 closed-caption stream (`0x06`) nor an ID3/metadata stream. Across the parsed video elementary stream not one SEI NAL unit arrives (nal types present: AUD, SPS, PPS, IDR, non-IDR slices), so the path hls.js needs for CEA-608 never starts: its caption code fires only on `user_data_registered_itu_t_t35` carrying country `0xB5`, provider `0x0031`, structure `GA94`, user data type 3, and the parser that reads it is proven against a synthetic message of exactly that shape before the negative is trusted.
- **The catalog's own vocabulary**: subtitles exist in the AniLibria model only as `torrents[].is_hardsub`, and the sampled Releases are 18 hardsub to 31 softsub torrents. Soft subs therefore live in the `.mkv` torrent payload that [ADR 0013](0013-hls-only-delivery-drops-bittorrent.md) took out of the product; the HLS tiers carry no subtitle field and no subtitle track. For the hardsub releases the picture already has its captions burned in and always shows them; for the rest there is simply nothing to display.

## Decision

- **Subtitles are not a feature of this product on this delivery.** The player renders no caption track, offers no subtitle row, and stores no subtitle Setting: there is no language to prefer, because no stream the app can play carries a text track. The capability mpv had does not get a webview successor now, and the loss stops being silent: it is measured, and the measurement is versioned with the code that would use it.
- **The caption lints are exempted in the lint policy, scoped to the one file that renders the media element** — `lint/a11y/useMediaCaption` for `src/features/player/ui/PlayerVideoViewport.tsx` in `biome.jsonc`'s `overrides`, `jsx-a11y/media-has-caption` for the same path in `.aislop/config.yml`'s `overrides`. No suppression comment survives in the source: the reason sits next to the rule it exempts, and the exemption names the file rather than the whole project, so a media element added anywhere else is still gated. `tests/test_caption_policy.test.ts` holds that arrangement: no directive anywhere in `src/`, Biome's recommended preset still in force with the rule on globally, the exemption pinned to the one path it is allowed to cover — and a second media element appearing anywhere fails the test instead of quietly widening the exemption.
- **The refusal is falsifiable, and the check is the probe, not a hunch.** Re-run `catalog_probe.py` and `cea608_probe.py` and revisit this ADR the moment any of these is true: a delivered playlist contains `#EXT-X-STREAM-INF` or `#EXT-X-MEDIA:TYPE=SUBTITLES` or names a `.vtt`/`.srt` URI; a segment's PMT declares `stream_type 0x06`; a video elementary stream carries a `GA94` SEI message.
- **What the refusal leaves unproven is stated, not hidden.** No code in the tree consumes a text track today, so the live pass could only record that the running stream produces none: `video.textTracks` stayed empty across the whole Episode sampled while the same element decoded and advanced. The positive path — hls.js handing the element a track and the app showing it — has therefore never been exercised, and the first step of the branch below must be a playlist that really carries a WebVTT rendition, built by hand, because no catalog stream can supply one. [#64](https://github.com/shidot3m/aniplayer/issues/64) asked for a run on a track-bearing stream; what this ticket delivers is the measurement that no such stream exists to run on.
- **What to build if the trigger fires** is the branch this ticket priced and rejected: read `hls.subtitleTracks` and the library's CEA-608 events in the playback session, mirror the selection into the store as a persisted Setting preferring `ru` then `en` in the old `--slang` order, add the row to the player menu when a track exists, and teach `prepare_local_playlist` in the Rust downloader to fetch subtitle renditions — otherwise an Offline Episode would lose what the online one had.

## Considered options

- **Build the subtitle plumbing now, so the capability is ready when the catalog grows tracks** — rejected: the code would be unreachable for every one of the measured playlists, its menu row never rendered, its Setting never readable, and the DOM would have to carry a permanently empty `<track kind="captions">` purely because a static lint cannot see a track that hls.js appends at runtime. That is the stub [AGENTS.md](../../AGENTS.md) refuses, dressed as a feature.
- **Keep the inline `biome-ignore`/`aislop-ignore-file` pair** — rejected: it is the shape #64 was opened for, a suppression whose comment argued about a decision nobody had taken.
- **Turn both caption rules off for the project** — rejected: it would also silence the gate for a media element that does get a text track later, and the refusal is about this element in this catalog, not about captions as a concept.
- **Let the user load their own `.srt`/`.vtt` file** — out of scope here: the catalog hands out no such file, and #64 is about the tracks the stream carries. It is a different product decision, and it would need its own source, its own persistence and its own accessibility case.

## Consequences

- The cost of the refusal is named rather than argued away. About half the sampled Releases carry their subtitles as a soft track in the torrent payload and none in the HLS tiers, so a viewer who needs captions does not get them from this app on those Episodes — and gets them from no other player on this CDN either, because the stream the app is handed has no text in it. Hardsub Releases show their captions always, in the picture. What this ticket fixes is the honesty of the record, not the accessibility of the catalog.
- `biome.json` became `biome.jsonc`. Biome parses a `.json` config strictly and rejects comments, and a rule switched off with no reason beside it is the unreadable stub this ticket exists to remove. Nothing referenced the filename, and aislop accepts both spellings.
- `--slang` has no successor in the settings surface. A user who asks for subtitles gets the answer the catalog allows: on a hardsub Episode they are already on screen, and on the rest the stream carries none — which is now stated in `docs/architecture.md` rather than left to the issue tracker.
- The downloader keeps the shape [ADR 0008](0008-local-hls-offline-downloads.md) describes: segment, init and key URIs are rewritten for offline play, master playlists are refused. When the trigger above fires, subtitle renditions join that list in the same change as the player work, not after it.
