# Живой прогон #61 — Anime4K через WebGPU поверх WebView-плеера

Портативная сборка этой машины: Windows 10.0.19045 x64, WebView2 Runtime 156.0.4314.58,
GPU — NVIDIA (Lovelace), экран 2560×1440. Артефакт: `bun run tauri:win build --no-bundle` →
`src-tauri/target/release/aniplayer.exe` → копия в `dist_portable/` (sha256 `1ebc88900b1952ef`
у обоих файлов, поэтому под прогоном ровно тот exe, который кладётся в архив релизным
workflow). `scripts/package_portable.py` пересоздаёт папку через `rmtree`, а `downloads/`
в этот момент был занят открытым хендлом, поэтому свежий бинарник был скопирован поверх
существующей portable-папки вместо пересоздания; состав артефакта от этого не меняется.

Управление — настоящие события ввода через remote-debugging-port WebView2 (9224):
`cdp.ps1` (клиент), `click.ps1` (клик по элементу/координатам, клавиши, `Shift+…`),
`emulate.ps1` (две ветки отказа GPU), `probe.ps1` (снимок живого webview),
`frame_diff.ps1` (сравнение двух скриншотов одного кадра), скриншоты —
`docs/evidence/60/win32.ps1 -Action shot`. Сырые снимки состояния — в `probe-log.txt`.

Серия: «Борьба в прямом эфире» (Kenka Dokugaku, 12 серий), онлайн-HLS, тир 720p/1080p.
Прогон сделан трижды: на первом артефакте, и по пересборке на каждом из двух исправлений,
которые он же и нашёл (повторная попытка после отказа адаптера, и скрытие элемента только
после первого отрисованного кадра) — цифры ниже сняты на финальном бинарнике.

## Рендерер поднимается сам из сохранённой настройки

После запуска приложения (без единого клика по тумблеру) серия открылась с уже включённым
апскейлом — настройка `anime4k_enabled=true` из `app_settings` применена, кадр фильтруется:

```
sample at launch: currentTime 266.9, paused false, frame 1280x720, video opacity 0,
                  canvas drawingBuffer 1280x720, badge "4K Upscale" = true
chunk timings:    PlayerOverlay.js start 91003 ms (25 ms),
                  anime4kRenderer.js start 91315 ms (113 ms), hls.js start 91317 ms (55 ms)
```

Тайминги чанков — доказательство ленивости в живом приложении: WebGPU-чанк запрашивается
сетью страницы только вместе с оверлеем плеера, а не на старте. В `index.html` его нет
(это же держит `tests/test_bundle_split.test.ts`).

## Один и тот же кадр: фильтрованный против сырого

Кадры сняты на одной и той же паузе (`currentTime` 172.2 в обоих снимках, меню закрыто в
обоих, контролы в одном состоянии), поэтому разница — только картинка:

```
frame_diff.ps1 -Before 05-frame-raw.png -After 04-frame-enhanced-aa.png
meanChannelDelta  = 2.366      changedPixelPct = 10.75
edgeEnergyBefore  = 5.202      edgeEnergyAfter = 10.853
```

Энергия границ (лапласиан по центральной полосе кадра) удваивается — это и есть то, что
делает Anime4K: восстановление контуров, а не перекраска кадра. Пресет в этом прогоне —
Mode A+A (HQ), тяжёлый двухпроходный.

## Реальный апскейл: canvas больше исходного кадра

В полноэкранном режиме на источнике 1080p (`06-fullscreen-upscaled.png`):

```
video.frame        = 1920x1080        (исходный кадр MSE)
canvas.drawingBuffer = 2560x1440      (размер, который отдал конвейер Anime4K)
canvas.display     = 2560x1440        (окно на экране 2560x1440)
video.opacity      = 0                (элемент скрыт под canvas)
```

Конвейер отдал текстуру 2560×1440 там, где декодированный кадр — 1920×1080: апскейл
происходит по-настоящему, а не «растягивание того же кадра».

## Пресет меняется на живом воспроизведении

`Shift+2` → Mode A+A, затем `Shift+3` → Mode B, без остановки сессии, на одной паузе
(`currentTime` 259 в обоих снимках):

```
edge energy:  A+A = 4.604   →   B = 3.954      (Mode B — мягкий Restore_Soft, меньше границ)
meanChannelDelta между пресетами = 0.495, изменено 1.86 % пикселей
app_settings после: ('anime4k_enabled', 'true'), ('anime4k_preset', 'Mode B (HQ)')
```

Разные пресеты дают разную картинку и разные строки в базе — то есть выбор применяется на
ходу и сохраняется как Setting.

## Воспроизведение под апскейлом не плывёт

На включённом A+A, онлайн-тир:

```
t0: currentTime 175.6, paused false, canvas 1280x720, badge true
t+8s: currentTime 184.0, paused false, canvas 1280x720, badge true
seek (→): 206.4 → продолжает идти; качество 1080p: frame 1920x1080, canvas 1920x1080,
          позиция 214.1 без перезапуска; обратно 720p — кадр и canvas меняются вместе
пауза/продолжение (Space) работают, оверлей контролов и меню не ломаются
```

Позиция идёт по часам элемента (картинка рисуется по `requestVideoFrameCallback`), звук
не перехватывается — синхронизация не плывёт.

Отдельно отмерен сам рассинхрон (`av_sync.ps1`, 4 с живого воспроизведения под A+A,
свой собственный `requestVideoFrameCallback`-наблюдатель рядом с рендерером):

```
frames 97 за 4.00 с медиа-времени (≈24 fps исходника, presentedFrames +96)
max |mediaTime − currentTime| = 8 ms,  медиана = 2 ms
canvas 1280x720 над video 1280x720, paused false
```

Рисуемый кадр отстаёт от аудио-часов не больше чем на один кадр источника — это и есть
«не плывёт»: картинка привязана к представленному каду, а не к собственному таймеру.

Сохранённость настроек между запусками — дамп той же базы, из которого приложение стартует
(в `probe-log.txt` метка `app_settings`):

```
anime4k_enabled    true
anime4k_preset     Mode A+A (HQ)
```

## Элемент не прячется раньше первого отрисованного кадра

Первая версия скрывала `<video>` в тот же миг, как переключатель включался, — то есть на
время загрузки чанка, запроса адаптера и сборки конвейера (≈100 мс) пользователь видел
чёрный canvas. Проверено под 20× троттлингом CPU, чтобы окно было заметным
(`paint_gate.ps1`, клик по тумблеру в момент t=0):

```
t=    3 ms canvas=False videoOpacity=1
t=  606 ms canvas=True  size=300x150   videoOpacity=1     ← canvas уже в DOM, кадр ещё не нарисован
t= 1160 ms canvas=True  size=300x150   videoOpacity=1
t= 1596 ms canvas=True  size=1280x720  videoOpacity=0     ← первый отрисованный кадр закрывает элемент
```

Элемент остаётся видимым, пока canvas пуст (размер 300×150 — дефолт canvas'а до первого
submit), и прячется ровно тогда, когда конвейер отдал первый кадр. Чёрной плашки нет ни в
один момент.

## Без WebGPU — отказ объяснён, остальное работает

WebView2 156 игнорирует `--disable-webgpu` и `--disable-features=WebGPU` (`navigator.gpu`
остаётся, адаптер отдаётся — проверено), поэтому отсутствие API смоделировано на живой
странице (`emulate.ps1 -Mode none` прячет геттер), а серия открыта заново:

```
webgpu.api = false
video.opacity = 1, canvas = null, badge = false
currentTime 8.2 → 11.9 (воспроизведение идёт)
меню плеера: aria-checked="false", disabled=true, в подсказке — «Нужен WebGPU»
```

Канвас поверх кадра не появляется вообще, контроль не обещает фильтрованный кадр,
остальные контролы (скорость, качество, пропуск OP/ED) активны.

## Отказ адаптера: кадр возвращается элементу, причина видна

`emulate.ps1 -Mode no-adapter` оставляет API, но `requestAdapter()` отвечает `null` — это
та ветка, где рендерер уже должен был поднять canvas:

```
меню: «Апскейлер 4K / WebGPU-адаптер не отдан машине»
aria-checked="false", canvas=false, video opacity=1
```

Черная плашка поверх живого кадра не осталась: при отказе canvas размонтируется, и
пользователь видит исходное изображение с объяснением в том же контроле.

Этот прогон нашёл дефект: в первой версии отказ так же блокировал и сам тумблер, поэтому
повторить попытку было нельзя до перезапуска приложения. Исправление (`setAnime4kEnabled`
снимает записанную причину, контроль остаётся кликабельным) проверено тем же прогоном на
пересобранном exe — `toggle_enhancement.ps1` кликает тумблер через живое меню плеера:

```
# адаптер снова отказывает, попытка включиться
before: checked=false disabled=False hintIsFault=False   (контроль не залочен)
after:  checked=false disabled=False hintIsFault=True    (причина видна)
surface: canvas=false videoOpacity=1 badge=false currentTime 523.8 → 528.2

# адаптер вернули, ещё одна попытка включиться
before: checked=false disabled=False hintIsFault=True
after:  checked=true  disabled=False hintIsFault=False
surface: canvas=true videoOpacity=0 badge=true  (`11-recovered-after-retry.png`)
```

То есть отказ адаптера стоит пользователю один клик, а не перезапуск, и ни одного кадра
чёрным канвасом не закрыто.

## Размер поставки

`bun run build` на этом же срезе (тот же артефакт, что внутри `aniplayer.exe`):

```
initial    index-*.js               369 kB  gz 110 kB   (бюджет ≤ 500 kB)
on-demand  PlayerOverlay-*.js        30 kB  gz   8 kB
on-demand  hls-*.js                 566 kB  gz 177 kB   (вместе ≤ 1 MB)
on-demand  anime4kRenderer-*.js    3374 kB  gz 934 kB   (свой ярус ≤ 3600 kB)
aniplayer.exe                      16.3 MB
```

WebGPU-чанк не входит в стартовый граф: `tests/test_bundle_split.test.ts` ищет его по WGSL-
декларации `texture_storage_2d<rgba16float, write>` и роняет сборку, если она появляется в
чанке из `index.html` или превышает ярус. В архиве по-прежнему только `aniplayer.exe` и
`data/` — папки шейдеров нет, таблицы шейдеров это JS-код внутри бандла.
